# Octacity Leaderboard

Monthly standings, teams, and the full contribution log of the
[Octacity](https://github.com/octacity-org) organization, built with SolidJS 2.0 (rc.15).

- **Standings**: top three of the month, totals against the previous month, the
  full member ranking, team ranking, six category boards, and a month-by-month
  roll of every board's leader.
- **Activity**: every commit, pull request, review, issue, discussion, and comment
  for the selected month, filterable by type, repository, and person.
- **Members**: teams with their leads and members, and a roster of every org member
  with all-time score, 15 per page.

The organization lead and team leads are not on GitHub, so they are kept by hand
in `src/roles.json`. Team leads are keyed by team slug:

```json
{
  "organizationLead": "ata-sesli",
  "teamLeads": { "aegis": "BerkeDurdu", "arc": "emreydin", "lucid": "akifkulll" }
}
```

The organization lead is not expected to be on a team, so they are not listed as unassigned.

## Run locally

```bash
bun install
```

```bash
bun run collect
```

```bash
bun run dev
```

`collect` writes `public/data.json` from the GitHub GraphQL API. It uses
`GH_TOKEN` or `GITHUB_TOKEN`, and falls back to `gh auth token`. The token needs
`read:org` to see org members and teams.

`public/data.json` is not committed. To run the site without a token, download
the published data instead of running `collect`:

```bash
curl -o public/data.json https://raw.githubusercontent.com/octacity-org/octacity-leaderboard/data/data.json
```

## How data is counted

- Only **public, non-fork** repositories are collected, because the output is published.
- Events dated before a repository joined the org are dropped, so imported
  repositories do not bring their upstream history.
- Commits are read from each default branch; merge commits are skipped.
- Only **org members** are ranked. Other contributors appear in Activity as guests.
- Months are UTC calendar months.

| Contribution | Points |
| --- | --- |
| Commit | 2 |
| Pull request opened | 3 |
| Pull request merged | 6 |
| Review (once per PR per reviewer) | 5 |
| Issue opened | 3 |
| Discussion started | 4 |
| Discussion reply | 2 |
| Issue or PR comment | 1 |

Scoring lives in `src/lib/rank.ts`, with tests in `src/lib/rank.test.ts`.

## Delivery

The Check, Build, and Ship workflows are generated by
[OmniShip](https://github.com/octacity-org/omniship) from `workflow.py`. Edit
`workflow.py`, then regenerate:

```bash
uvx --from omniship==0.2.0 omniship generate
```

Ship deploys `dist/` to GitHub Pages on every push to `main` and on manual dispatch.

OmniShip does not support scheduled triggers, so `.github/workflows/refresh.yml`
is written by hand. It runs hourly at minute 17, collects fresh data, and
force-pushes it as the only commit on the `data` branch. The deployed site
fetches `data.json` from that branch through raw.githubusercontent.com, so data
updates do not commit to `main` or redeploy. GitHub caches the file for about
5 minutes, so new data can take up to ~10 minutes to appear.

Repository setup:

1. Create a GitHub App owned by the organization (*Organization settings →
   Developer settings → GitHub Apps → New GitHub App*):
   - Webhook: turn off *Active*.
   - Repository permissions, all read-only: *Contents*, *Issues*, *Pull requests*,
     *Discussions* (*Metadata* is added automatically).
   - Organization permissions: *Members*: read-only.
   - Installable only on this account.
2. Generate a private key on the app's page, then install the app on the
   organization with access to all repositories.
3. In this repository, add a `LEADERBOARD_APP_CLIENT_ID` variable (the app's
   Client ID) and a `LEADERBOARD_APP_PRIVATE_KEY` secret (the whole `.pem` file).
4. Set GitHub Pages to deploy from GitHub Actions.
